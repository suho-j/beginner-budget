# 가계부 V2 반복지출·예정 내역 설계

- 작성일: 2026-08-12
- 상태: 대화 설계 승인, 문서 사용자 검토 대기
- 기준 버전: V1 소스 `2b7d34f`
- 개발 브랜치: `guardian/budget-preview-v2`
- 예상 공개 경로: `https://suho-j.github.io/beginner-budget-preview/v2/`

## 1. 독자와 목적

이 문서의 독자는 V2를 구현하고 검증할 개발자다. 문서를 읽은 뒤 운영 사이트와 V1 미리보기를 바꾸지 않고 반복지출 V2를 구현해 별도 URL에 배포할 수 있어야 한다.

V2의 사용자 목표는 입문자가 매달 되풀이되는 지출을 미리 확인하고, 실제 결제일과 금액을 한 번 검토한 뒤 안전하게 거래로 기록하는 것이다. 은행 연동이나 자동 기록 없이도 “곧 나갈 돈을 놓치지 않고 실제 지출을 중복 없이 남기는 것”을 성공 기준으로 삼는다.

## 2. 배경과 선택 근거

주요 가계부의 공통 패턴은 `반복 규칙 → 예정 항목 → 실제 발생 확인 → 완료`다. V2는 이 흐름을 은행 연동 없는 정적 앱에 맞게 축소한다.

화면 배치는 다음 세 안을 비교했다.

1. 홈 요약 아래에서 예정 목록과 기록 버튼을 바로 제공
2. 홈에는 예정 합계만 제공하고 상세 화면을 한 번 더 열기
3. 다섯 번째 `예정` 탭 추가

사용자는 첫 번째 안을 선택했다. 기존 네 탭과 360px 키보드 구조를 유지하면서 예정 항목을 놓치기 가장 어렵기 때문이다.

기록 흐름도 세 안을 비교했다.

1. 작은 확인 창에서 날짜와 금액을 검토한 뒤 저장
2. 예정 목록 행을 펼쳐 바로 편집
3. 기존 거래 입력 폼으로 이동해 저장

사용자는 첫 번째 안을 선택했다. 목록 맥락을 보존하면서도 변동 금액과 실제 결제일을 저장 전에 확인할 수 있기 때문이다.

## 3. 범위

### 포함

- 매월 한 번 반복되는 지출 템플릿 추가·수정·삭제
- 선택한 예산기간에 포함되는 예정 항목 계산
- 홈의 `예정된 반복지출` 목록
- `예정 · 오늘 · 지남 · 기록됨` 상태
- 확인 창에서 실제 날짜·금액·카테고리·메모 검토 및 수정
- 확인 후 일반 지출 거래 한 건 원격 우선 저장
- 교차 브라우저·연속 클릭 중복 방지
- V1 데이터와 V1 백업의 무손실 V2 승격
- V2 백업·가져오기·초기화·샘플·로그아웃 경로
- 360px, 키보드, 스크린리더 상태 알림
- V1과 분리된 V2 미리보기 데이터 복사본과 `/v2/` 공개 URL

### 제외

- 수입 반복 규칙
- 매주·격주·분기·연간 등 월간 외 주기
- 종료일, 일시정지, 이번 회차 건너뛰기
- 사용자의 확인 없는 자동 거래 생성
- 은행·카드 연동과 자동 매칭
- 이메일·푸시 알림
- 계좌 잔액 기반 현금흐름 또는 `쓸 수 있는 돈` 계산
- V2 검수 전 운영 `master` 또는 운영 데이터 변경

## 4. 사용자 경험

### 4.1 홈 예정 목록

홈 요약 바로 아래에 `예정된 반복지출` 섹션을 둔다. 선택한 예산기간의 항목만 예정일 순으로 표시한다.

각 항목은 다음 정보를 제공한다.

- 상태: `예정`, `오늘`, `지남`, `기록됨`
- 예정일
- 이름
- 카테고리
- 예상 금액
- 미기록 항목의 `기록하기` 버튼

섹션 머리에는 **미기록 건수와 미기록 예상 합계**를 표시한다. 예상 합계는 안내용이며 실제 총지출, 예산 사용률, 남은 예산, 카테고리 지출, 캘린더 합계에 포함하지 않는다. `자동 결제 완료` 같은 표현을 사용하지 않는다.

미기록 항목을 먼저, 기록된 항목을 뒤에 둔다. 같은 상태에서는 예정일과 이름 순으로 정렬한다. 항목이 없으면 반복지출을 설정에서 등록할 수 있다는 짧은 안내를 보여준다.

상태 판정 우선순위는 다음과 같다.

1. 결정적 거래 ID가 있으면 날짜와 관계없이 `기록됨`
2. 미기록이고 예정일이 로컬 오늘보다 과거면 `지남`
3. 미기록이고 예정일이 로컬 오늘이면 `오늘`
4. 미기록이고 예정일이 미래면 `예정`

미기록 행은 템플릿의 예정일과 예상 금액을 표시한다. 기록된 행은 연결된 거래의 실제 사용일과 실제 금액을 표시해 사용자가 수정 결과를 확인할 수 있게 한다.

### 4.2 기록 확인 창

`기록하기`를 누르면 거의 전체 폭의 네이티브 대화상자가 열린다. 다음 값을 예정 템플릿으로 채운다.

- 사용일: 원래 예정일
- 실제 금액: 예상 금액
- 카테고리
- 메모: 템플릿 이름

사용자는 네 값을 모두 수정할 수 있다. `지출로 기록`을 누르면 기존 거래 검증 규칙을 적용하고, 성공 전에는 창을 닫거나 메모리 상태를 바꾸지 않는다.

저장 성공 후 해당 항목을 `기록됨`으로 바꾸고 홈 요약·내역·캘린더를 다시 그린다. 사용일을 다른 예산기간으로 바꿨다면 거래가 현재 캘린더에 보이지 않는 이유를 성공 메시지로 알린다.

취소하면 원격 호출과 상태 변경이 없다. 실패하면 입력값과 포커스를 유지한다. 이미 다른 브라우저에서 기록한 항목이면 기존 거래를 덮어쓰지 않고 `이미 기록된 항목이에요. 최신 내용을 다시 불러와 주세요.`라고 안내한다.

### 4.3 설정의 반복지출 관리

설정 탭에 `반복지출 설정` 섹션을 추가한다. 등록 폼은 다음 네 입력만 사용자에게 노출한다.

- 이름
- 카테고리
- 예상 금액
- 매월 결제일 1~31

등록된 템플릿은 이름·카테고리·금액·결제일과 `수정`, `삭제` 동작을 제공한다. 수정과 삭제는 아직 기록하지 않은 발생 건과 미래 발생 건에만 영향을 준다. 이미 생성된 일반 거래는 유지한다.

## 5. 도메인과 상태

### 5.1 상태 버전

정규화된 앱 상태의 버전을 `2`로 올리고 다음 배열을 추가한다.

```json
{
  "version": 2,
  "recurringExpenseTemplates": [
    {
      "id": "rt-<uuid>",
      "memo": "통신비",
      "category": "생활비",
      "amount": 55000,
      "dayOfMonth": 25,
      "startsOn": "2026-08-12"
    }
  ]
}
```

화면의 `이름`은 거래와 같은 80자 제한을 재사용하기 위해 상태에서 `memo`로 보관한다. `type`은 항상 `expense`이므로 템플릿에 저장하지 않는다.

### 5.2 템플릿 정규화

각 템플릿은 다음 계약을 만족해야 한다.

- `id`: 안전한 ASCII ID이며 새 항목은 `rt-<uuid>` 형식
- `memo`: 공백 제거 후 1~80자
- `category`: 현재 지출 카테고리 중 하나
- `amount`: 1 이상 DB 정수 상한 이하의 정수
- `dayOfMonth`: 1~31 정수
- `startsOn`: 실제 존재하는 로컬 `YYYY-MM-DD` 날짜
- 배열 내 ID 중복 없음
- 정규화된 템플릿 최대 100개

기존 V1 상태나 예약 키가 없는 원격 설정은 빈 배열로 승격한다. 버전 2보다 큰 백업은 알 수 없는 필드를 조용히 버리지 않고 가져오기를 거부한다.

새 템플릿의 `startsOn`은 등록 버튼을 누른 로컬 날짜다. 템플릿을 수정할 때는 기존 `id`와 `startsOn`을 그대로 보존한다. 따라서 결제일을 수정해도 등록 이전 달이 새 미납 항목으로 생기지 않는다.

### 5.3 예정 발생 건

예정 발생 건은 저장하지 않는다. 선택한 예산기간과 템플릿에서 매번 파생한다.

1. 예산기간과 겹치는 모든 달을 구한다.
2. 각 달의 예정일을 `min(dayOfMonth, 그 달의 마지막 날)`로 계산한다.
3. 예정일이 예산기간 안이고 `startsOn` 이상인 건만 남긴다.
4. 템플릿 ID와 예정 달 `YYYY-MM`로 발생 키를 만든다.

31일 규칙은 2월에 28일 또는 29일로 보이지만 규칙값 31을 유지한다. 따라서 3월에는 다시 31일로 돌아온다. 예산 시작일은 표시 범위만 정하며 반복 결제일 자체를 바꾸지 않는다.

예를 들어 시작일이 25일인 `2026-05` 예산기간은 `2026-05-25~2026-06-24`다. 결제일 5일 템플릿은 이 기간에서 `2026-06-05` 한 건으로 계산한다. 인접 예산기간에 같은 발생 건이 중복돼서는 안 된다.

### 5.4 확정 거래 ID

확정 거래 ID는 다음 정보로 결정적으로 만든다.

```text
tx-recurring-<template-id>-<scheduled-YYYY-MM>
```

한 템플릿은 달마다 한 번만 발생하므로 예정 달이 발생 건의 안정된 키다. 사용자가 확인 창에서 실제 날짜를 바꾸거나 템플릿 결제일을 나중에 수정해도 이미 기록한 달은 다시 나타나지 않는다.

기록 여부는 이 거래 ID의 존재만으로 판단한다. 금액·날짜·카테고리·메모를 나중에 수정해도 기록 상태를 유지한다. 거래를 삭제하면 발생 ID가 없어져 해당 달의 항목이 다시 미기록으로 나타난다. 이 동작은 삭제 확인문에 안내한다.

## 6. 클라우드 저장과 동시성

### 6.1 템플릿 저장

템플릿 배열은 `budget_settings.category_budgets`의 예약 키 `__recurring_expense_templates`에 저장한다. 별도 운영 도메인 테이블이나 RPC 시그니처는 추가하지 않는다.

템플릿 추가·수정·삭제는 기존 설정 `updated_at` 비교를 사용하는 원격 우선 흐름으로 처리한다.

1. 현재 상태에서 다음 상태를 순수 함수로 만든다.
2. 설정 저장 버튼을 잠근다.
3. 예상 `updated_at`과 일치할 때만 원격 설정을 저장한다.
4. 성공한 뒤에만 메모리 상태와 폼을 갱신한다.
5. 충돌하면 로컬 변경을 확정하지 않고 재다운로드를 요구한다.

예약 키는 기본 상태, 정규화, 원격 매핑, 전체 교체 인자, 다운로드 복원에 모두 포함한다. 일반 카테고리 예산 목록에는 예약 키를 노출하지 않는다.

### 6.2 발생 건 기록

발생 건 확인은 별도의 `다음 실행일`을 갱신하지 않고 일반 거래 한 건만 insert한다. 이 경계는 거래 저장과 일정 이동이 따로 성공하는 부분 실패를 없앤다.

저장 중에는 확인 창의 제출 버튼과 다른 클라우드 쓰기를 잠근다. 동일 ID insert의 DB 기본 키 충돌을 최종 중복 판정자로 사용한다. 중복 오류에서 upsert하지 않는다. 최신 데이터를 다시 읽어 같은 ID가 있으면 이미 기록된 상태로 안내하고, 없으면 일반 저장 오류로 처리한다.

### 6.3 버전별 미리보기 격리

V1과 V2를 동시에 검수해도 서로 설정을 덮어쓰지 않도록 V2는 별도의 미리보기 복사본을 사용한다.

- V2 설정: `preview_v2_budget_settings`
- V2 거래: `preview_v2_transactions`
- V2 전체 교체 RPC: `replace_preview_v2_budget_state`
- 일회 seed marker: `production_snapshot_v2`

이는 운영 도메인 스키마 변경이 아니라 V2 검수용 데이터 namespace다. V2 SQL은 운영 객체를 읽기·일관성 잠금 원본으로만 사용하고 운영 DDL·DML·권한을 바꾸지 않는다. V1의 `preview_*` 객체와 데이터도 변경하지 않는다.

최초 seed는 V1에서 검증한 것과 같은 짧은 전 환경 쓰기 중단 창, 충돌 guard, 양방향 canonical 비교, 영구 marker 계약을 따른다. V2 개발 브랜치는 로컬·알 수 없는 호스트·미리보기 저장소의 `/v2/`에서 `preview_v2_*` 객체만 사용한다. 운영 객체는 정확한 HTTPS 운영 origin과 `/beginner-budget/` 경로가 모두 일치할 때만 선택한다. 그 밖의 환경은 운영으로 fail-open하지 않는다.

운영 승격 시에는 모든 구버전 탭과 쓰기를 중단하고, 백업·감사·SQL 적용·정확한 안전 SHA 승격·운영 다운로드와 스모크가 끝날 때까지 하나의 배타적 쓰기 창을 유지한다. 사용자가 V2 URL을 선택하기 전에는 이 절차를 실행하지 않는다.

## 7. 전체 상태 경로

- 내보내기: 정규화된 템플릿과 확정 거래 ID를 그대로 포함한다.
- 가져오기: V1은 템플릿 빈 배열로 승격한다. V2는 템플릿을 검증한다. 유효 거래와 유효 템플릿이 모두 0건일 때만 빈 가져오기로 거부하며, 확인문에 거래 건수와 템플릿 건수를 함께 표시한다.
- 전체 초기화: 거래·예산·템플릿을 모두 초기값으로 교체한다.
- 샘플 채우기·교체: 사용자 템플릿을 보존한다.
- 다운로드: 원격 예약 키가 없으면 빈 배열을 사용한다.
- 로그아웃: 메모리의 템플릿, 파생 예정 목록, 열려 있는 확인 창과 입력값을 모두 비우고 쓰기를 잠근다.

가져오기와 초기화는 설정 버전과 전체 거래 스냅샷을 함께 비교하는 기존 원자적 전체 교체 흐름을 유지한다.

## 9. 오류 처리와 접근성

- 모든 템플릿 입력에 보이는 label과 오류 설명 연결을 제공한다.
- 홈 섹션은 전체 목록이 아니라 건수·저장 결과만 polite live region으로 알린다.
- `기록하기` 버튼 이름에 예정일·이름·금액을 포함한다.
- 확인 창을 열면 사용일 입력으로 포커스를 옮긴다.
- Tab은 창 안에서 이동하고 Escape와 취소로 닫을 수 있다.
- 취소하면 호출 버튼으로, 저장 후 항목이 사라지면 섹션 제목으로 포커스를 복원한다.
- 템플릿 삭제 후에는 다음 템플릿 행 또는 섹션 제목으로 포커스를 복원한다.
- 저장 실패 시 첫 오류 입력으로 포커스를 옮기되 다른 입력값을 유지한다.
- 모든 주요 터치 대상은 최소 44px이며 360px에서 한 열로 배치한다.
- 긴 이름과 큰 금액은 문서 가로 스크롤 없이 줄바꿈한다.

## 10. 검증 계약

새 로직은 실패 테스트를 먼저 추가한 뒤 최소 구현과 리팩터링 순서로 진행한다.

### 자동 테스트

- V1 상태·원격 설정·백업을 템플릿 빈 배열로 승격
- 미래 상태 버전 거부
- 템플릿 유효값, 무효값, ID 중복, 100개 상한, DB 정수 상한
- 템플릿만 있는 백업의 export/import
- 예산 시작일 25일과 두 달 경계
- 윤년·비윤년 2월과 결제일 29~31
- 인접 예산기간 발생 건 비중복
- 결제일 수정 뒤 이미 기록한 예정 달의 상태 유지
- 확인 전 요약·내역·캘린더 불변
- 확인 취소 시 원격 호출 0회
- 확인 성공 뒤 홈·요약·내역·캘린더 갱신
- 실제 날짜를 다른 기간으로 수정한 성공 메시지
- 연속 클릭 1회 요청과 교차 브라우저 PK 충돌
- 설정 CAS 충돌과 거래 insert 실패 시 로컬 상태·입력 유지
- 확정 거래 수정 후 기록 상태 유지, 삭제 후 재등장
- 템플릿 CRUD가 원격 성공 후에만 폼과 상태를 변경
- 가져오기·초기화·샘플·다운로드·로그아웃 전체 경로
- production, V1 preview, V2 preview 환경 라우팅
- V1 객체와 운영 객체를 V2 SQL이 변경하지 않는 구조 계약

### 브라우저 검증

- 로그인 후 템플릿 추가·수정·삭제
- 예정·오늘·지남·기록됨 상태와 예상 합계
- 쉼표 금액을 확인 창에서 수정해 기록
- 취소, 오류, 중복 충돌, 포커스 복원
- 확정 거래가 요약·내역·캘린더에 한 번만 반영
- 키보드만으로 템플릿 관리와 확인 창 사용
- 360×800에서 가로 넘침 없음, 44px 터치 영역
- 콘솔 오류 0건

### 데이터베이스 검증

격리된 PostgreSQL과 staging Supabase에서 다음을 검증한다.

- V2 preview seed의 원자성·재실행 불변·V1/운영 비변경
- 사용자별 RLS와 최소 권한
- 설정 `updated_at` 단조 증가와 CAS 충돌
- 전체 교체 5인자 RPC 성공·stale 40001·롤백
- 동일 확정 거래 ID의 동시 insert 중 하나만 성공
- 두 세션 seed·설정·전체 교체 잠금 순서에 deadlock 없음

## 11. 문서와 배포

구현과 함께 데이터 모델, 실행 안내, 테스트 계획, 개선 로그, 수동 체크리스트를 실제 동작에 맞춰 갱신한다. 반복 거래 제외나 브라우저 저장을 주장하는 오래된 요구사항·계획은 superseded 상태를 명시한다.

V2 산출물은 V1과 별도로 `/v2/`에 복사하고 소스 브랜치와 정확한 SHA를 버전 매니페스트에 기록한다. 공개 URL에서 자동·브라우저·인증 저장 검증이 모두 통과해도 운영에는 반영하지 않는다. 사용자가 선택한 URL과 SHA만 운영 승격 후보가 된다.

## 12. 완료 조건

- 승인된 홈 예정 목록과 확인 창이 구현됐다.
- 템플릿과 예정 발생 건의 경계·말일·중복 규칙이 테스트로 고정됐다.
- 예상 항목이 실제 예산·지출에 이중 합산되지 않는다.
- 템플릿 CAS와 확정 거래 PK 충돌에서 원격 성공 전 로컬 상태가 바뀌지 않는다.
- V2 preview 데이터, SQL, URL이 V1과 운영에서 격리됐다.
- 자동 테스트, syntax, diff, UTF-8, 접근성, 360px, 콘솔 검증이 통과했다.
- 실제 PostgreSQL과 Supabase 인증 저장 경로를 검증했다.
- 공개 `/v2/` URL과 소스 SHA를 사용자에게 제공했다.
- 운영 `master`와 운영 데이터는 사용자가 특정 버전을 승인하기 전까지 변경되지 않았다.
