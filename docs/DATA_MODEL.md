# 데이터 모델

이 문서는 V2 앱이 메모리, JSON 백업, Supabase 사이에서 유지해야 하는 데이터 계약을 설명합니다. 가계부 데이터의 기준 저장소는 Supabase Auth + RLS 영역이며, 브라우저 `localStorage`에는 예산·거래·반복지출 데이터를 저장하지 않습니다. 브라우저 저장소는 Supabase 인증 세션 유지에만 사용될 수 있습니다.

## V2 상태

```json
{
  "version": 2,
  "monthlyBudget": 500000,
  "categoryBudgets": {
    "생활비": 200000,
    "배달비": 100000
  },
  "monthStartDay": 25,
  "monthlyBudgets": {
    "2026-08": {
      "monthlyBudget": 700000,
      "categoryBudgets": {
        "생활비": 300000
      }
    }
  },
  "recurringExpenseTemplates": [
    {
      "id": "rt-7e42c4d0",
      "memo": "월세",
      "category": "생활비",
      "amount": 550000,
      "dayOfMonth": 31,
      "startsOn": "2026-08-12"
    }
  ],
  "transactions": [
    {
      "id": "tx-recurring-rt-7e42c4d0-2026-09",
      "date": "2026-09-30",
      "type": "expense",
      "category": "생활비",
      "amount": 550000,
      "memo": "월세",
      "source": "user"
    }
  ]
}
```

- `version`: 현재 상태 버전은 정수 `2`입니다.
- `monthlyBudget`, `categoryBudgets`: 월별 값이 없을 때 사용하는 기본 총예산과 지출 카테고리 예산입니다.
- `monthStartDay`: 예산 기간 시작일인 1~31 사이 정수입니다. 존재하지 않는 말일은 해당 월의 마지막 날로 보정합니다.
- `monthlyBudgets`: `YYYY-MM`로 선택한 예산 기간별 총예산과 카테고리 예산입니다.
- `transactions`: 실제 합계와 캘린더에 반영되는 수입·지출입니다.
- `recurringExpenseTemplates`: 예정 항목을 계산하기 위한 반복지출 설정입니다. 템플릿 자체는 실제 지출이 아닙니다.

## 항목 간 예산 이동 계약

항목 간 예산 이동은 새 상태 필드, 거래 행, 별도 Supabase 테이블을 만들지 않습니다. 선택한 `YYYY-MM`의 `monthlyBudgets[month].categoryBudgets`에서 출발 항목 예산을 줄이고 도착 항목 예산을 같은 금액만큼 늘립니다.

- 출발과 도착은 `생활비`, `배달비`, `의류비`, `비상금`, `휴가비` 중 서로 다른 항목이어야 합니다.
- 이동 가능액은 `max(출발 항목 예산 - 선택 예산기간의 출발 항목 실제 지출, 0)`입니다. 기간 판정은 `monthStartDay`를 따릅니다.
- 이동액은 1~2,147,483,647 사이 정수이며 쉼표 입력을 정규화합니다. 이동 뒤 도착 항목 예산도 같은 DB 정수 상한을 넘지 않아야 합니다.
- 출발 항목의 이동 후 예산이 0원이면 해당 키를 생략합니다. 월 총예산, 항목 예산 합계, 실제 거래와 반복지출 템플릿은 바뀌지 않습니다.
- `BudgetCloud.saveSettings`의 `updated_at` CAS가 성공한 뒤에만 메모리 상태를 바꿉니다. 충돌이나 네트워크 실패 시 기존 예산과 폼 입력을 유지합니다.

## 반복지출 템플릿 계약

템플릿은 다음 여섯 필드를 모두 가집니다.

| 필드 | 계약 |
| --- | --- |
| `id` | `rt-`로 시작하고 영문, 숫자, `.`, `_`, `:`, `-`만 사용하는 고유 ID |
| `memo` | 앞뒤 공백을 제거한 1~80자 이름 |
| `category` | 지출 카테고리 `생활비`, `배달비`, `의류비`, `비상금`, `휴가비` 중 하나 |
| `amount` | 1~2,147,483,647 사이 정수 |
| `dayOfMonth` | 매월 발생일인 1~31 사이 정수 |
| `startsOn` | 템플릿을 만든 로컬 날짜 `YYYY-MM-DD` |

상태 정규화는 잘못된 템플릿을 제외하고, 중복 ID는 처음 한 건만 유지하며, 최대 100개까지만 보존합니다. 템플릿 수정은 `id`와 `startsOn`을 유지합니다. 사용자 입력도 같은 이름·카테고리·금액·발생일 규칙을 통과해야 합니다.

## Supabase 매핑과 예약 키

예산 설정 한 행의 `category_budgets` JSON에는 일반 카테고리 예산과 내부 설정이 함께 저장됩니다.

- `__month_start_day`: 예산 시작일
- `__monthly_budgets`: 월별 예산
- `__recurring_expense_templates`: 반복지출 템플릿 배열

`__recurring_expense_templates`를 포함해 `__`로 시작하는 키는 예약 키입니다. 카테고리 예산 정규화·합계·화면 목록에서는 일반 카테고리로 취급하지 않습니다. V2 미리보기는 `preview_v2_budget_settings`, `preview_v2_transactions`, `replace_preview_v2_budget_state`만 사용합니다.

## 예정 항목은 파생 데이터

예정 항목(occurrence)은 DB나 JSON에 별도 저장하지 않습니다. 선택한 예산 기간, 템플릿, 실제 거래를 합쳐 화면을 그릴 때 계산합니다. 예산 시작일이 1일이 아니면 한 예산 기간에 두 달의 예정 항목이 포함될 수 있습니다.

- `dayOfMonth`가 그 달에 없으면 예정일만 월말로 보정합니다. 예를 들어 31일 설정은 2월 28일 또는 29일에 표시되지만 템플릿 값은 계속 `31`입니다.
- `startsOn`보다 이른 예정일은 만들지 않습니다.
- 미기록 예정 금액은 수입·지출·잔액·예산 사용률·카테고리 합계·캘린더에 포함하지 않습니다.
- 정렬 순서는 상태, 예정일, 이름, 템플릿 ID 순입니다.

상태와 화면 라벨은 다음과 같습니다.

| 상태 | 화면 라벨 | 판정 |
| --- | --- | --- |
| `overdue` | 지남 | 거래가 없고 예정일이 오늘보다 이전 |
| `today` | 오늘 | 거래가 없고 예정일이 오늘 |
| `upcoming` | 예정 | 거래가 없고 예정일이 오늘보다 이후 |
| `recorded` | 기록됨 | 결정적 거래 ID와 같은 실제 거래가 있음 |

표시와 정렬의 상태 우선순위는 `지남 → 오늘 → 예정 → 기록됨`입니다.

## 결정적 거래 ID와 수명주기

반복지출을 확정하면 거래 ID를 다음 형식으로 만듭니다.

```text
tx-recurring-<templateId>-<YYYY-MM>
```

마지막 `YYYY-MM`은 사용자가 확인 창에서 바꾼 실제 사용일의 달이 아니라, 원래 예정일이 속한 달입니다. 예를 들어 2026년 9월 예정 항목의 사용일을 10월 1일로 바꿔도 ID 끝은 `2026-09`입니다.

기록 여부는 이 ID의 존재만으로 판단합니다. 날짜·금액·카테고리·메모를 나중에 수정해도 ID가 유지되므로 `기록됨` 상태도 유지됩니다. 현재 템플릿과 예정 월이 유효한 상태에서 확정 거래를 삭제하면 같은 ID가 사라져 예정 항목이 다시 나타납니다. 템플릿을 수정하거나 삭제해도 이미 확정된 거래는 바뀌거나 삭제되지 않으며, 이후 파생되는 예정 항목에만 영향을 줍니다.

## 백업 내보내기·가져오기

- 내보내기는 정규화한 전체 상태를 버전 2 JSON으로 만듭니다. 템플릿과 확정 거래가 함께 포함됩니다.
- 버전이 없거나 `1`인 백업은 V1로 보고 거래와 예산을 승격하되 템플릿은 항상 빈 배열로 시작합니다.
- 버전 2 백업은 유효한 거래와 템플릿을 정규화해 가져옵니다.
- 현재 앱보다 높은 버전, 정수가 아닌 버전, 배열이어야 하는 필드가 다른 형식인 백업은 거부합니다.
- 유효한 거래와 유효한 템플릿이 모두 0건이면 현재 데이터를 지우지 않고 가져오기를 중단합니다.
- 앱은 1MB를 넘는 가져오기 파일을 거부합니다.
- 가져오기·전체 초기화·샘플 교체는 설정 버전과 전체 거래 스냅샷을 비교하는 원자적 CAS RPC를 거쳐 성공한 뒤에만 화면 상태를 바꿉니다.

## 복구 원칙

클라우드 다운로드나 로컬 정규화에서 잘못된 개별 행은 제외하고 유효한 데이터는 유지합니다. 다른 브라우저의 선행 변경, 손상된 백업 배열, 미래 버전 백업은 자동 덮어쓰기로 복구하지 않습니다. 사용자가 최신 클라우드 상태를 다시 불러오거나 올바른 백업을 선택하도록 안내합니다.
